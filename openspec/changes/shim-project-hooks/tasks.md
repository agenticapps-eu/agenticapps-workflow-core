## 3. Publish and verify before touching any project

- [ ] 3.1 Add a multi-artifact install step so both implementations can be provisioned in one invocation, rather than one artifact per call
- [ ] 3.2 `tdd="true"` — failing test: the installer reports failure when a shimmed implementation is absent or not executable. This verification is where the guarantee lives now that shims fail open
- [ ] 3.2a `tdd="true"` — failing test: the installer writes a manifest beside the shared install directory with one row per artifact (path, version marker, `sha256` lowercase hex), and an on-demand check reports an executed copy that has been hand-edited or replaced. "Present and executable" accepts stale and tampered code
- [ ] 3.2a-i Implement the manifest check as a conformance tool, not in any shim's hot path — no shim hashes its implementation before invocation
- [ ] 3.2a-ii Report the manifest check (executed copy vs. what was published) separately from the stronger source check (executed copy vs. the maintained file in core, which requires core on the machine). Do not conflate them
- [ ] 3.2a-iii Document the property as drift detection, not tamper-proofing: the manifest is unsigned and sits beside the artifact under the same ownership, so anyone who can alter the implementation can alter its row
- [ ] 3.2b **REWRITTEN — the previous wording specified something impossible.** It said "make multi-artifact publication atomic … updating each artifact's manifest row in the same operation as the file it describes". Two `rename(2)` calls are two operations, and per-file renames do not compose into a multi-file transaction. Implement the achievable guarantee instead: each implementation is written to a temporary path **in the destination directory** and `rename`d into place (design Decision 12)
- [ ] 3.2b-i Rewrite the manifest **in full** to a temporary path and `rename` it — never edit rows in place. Row-wise editing has its own torn-write window, and whole-file replacement makes the manifest's update atomic even though it cannot be joined to the artifact's
- [ ] 3.2b-ii `tdd="true"` — failing test: two concurrent publishing runs do not lose each other's manifest rows. Hold an **exclusive lock** for the critical section. This is a lost-update defect, which atomicity does not address and which nothing in the previous revision mentioned
- [ ] 3.2b-iii Rename each artifact into place **before** publishing the manifest row naming it, so the reachable inconsistency is "present but unattested" rather than "attested but absent". State the reason: an unverifiable-but-working hook degrades to a warning; a row pointing at nothing reports a failure the operator cannot act on
- [ ] 3.2c `tdd="true"` — failing test: killing the installer between two artifacts leaves every **published** implementation complete rather than truncated, and the manifest either the pre-run or post-run version, never a torn mixture. The machine is left **partially provisioned** — a legitimate state the check reports, not an invariant the installer promises cannot occur
- [ ] 3.2c-i `tdd="true"` — failing test: an artifact renamed into place before a crash, with no manifest row, is reported **unverifiable** — not absent, and not a clean install
- [ ] 3.2d Implement the **four** provisioning states the delta defines — unprovisioned / partially provisioned / provisioned / **drifted** — and confirm each invariant is stated against its own state. The previous revision asserted "no project binds a hook whose implementation is absent" globally while the clone-before-install scenario permitted exactly that
- [ ] 3.2d-i **Compute every state observationally, never from history.** "The installer has never run" and "a publishing run completed" are not evaluable after the fact and classified a completed-then-deleted or hand-edited install as *provisioned* — the exact condition the manifest check exists to detect (design Decision 12, round-8 codex)
- [ ] 3.2d-ii `tdd="true"` — failing test: an install that completed and was then hand-edited, replaced or partially deleted reports **drifted**, not provisioned and not unprovisioned
- [ ] 3.2e **Implement the publication algorithm as written, once per run:** lock → read manifest → rename every artifact into place → rewrite the manifest in full once → unlock. The previous text specified a manifest written once per run *and* a row published per artifact, which cannot both hold
- [ ] 3.2e-i `tdd="true"` — failing test for the **upgrade** crash the previous revision never covered: republishing over an artifact that already has a row, interrupted before the manifest rewrite, leaves the new bytes against the **old row** — a stale row, not a missing one. It reports **drifted**; "present but unattested" and "clean" are both wrong. Remedy in both crash cases is re-running the installer
- [ ] 3.3 Publish both to `~/.agenticapps/bin/` and confirm they are present and executable
- [ ] 3.4 Verify each published implementation behaves identically to the project copy it replaces, **apart from the dropped `migrations/` clause**, tested against the repo whose copy was canonical
- [ ] 3.5 Verify the reconciled `database-sentinel` against a repo that previously used the enumerated `.env` list, confirming it now catches a novel suffix
- [ ] 3.6 `tdd="true"` — failing test: a conformance check reports the **machine's** provisioning state, computed per 3.2d, independently of any repository check. Every other check this change specifies is per-repo (markers, byte-identity, the settings scan) and none of them can see whether this machine holds the implementations
- [ ] 3.6a **Record the regression this answers, rather than only the check.** Before the change, `database-sentinel` ran on any clone with zero provisioning because the implementation was in the clone; after it, protection travels with the machine and **every existing developer machine enters the unprovisioned state the moment it pulls the shim** — an ordinary `git pull`, no prompt to install (round-8 opencode)
- [ ] 3.6b Publish-and-verify orders exactly **one** machine — the rollout machine. Do not cite it as fleet-wide assurance. Tell the fleet to run the installer; ordering on one machine constrains no other
